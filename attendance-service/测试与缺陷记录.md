## 二、缺陷记录

### BUG-01（设计类 · 高）工时服务无法获取岗位时薪与部门

- **发现人**：成员 5　　发现日期：2026-11-17　　状态：已修复（成员 4）
- **现象**：核算补贴需要「时薪 × 工时」，但岗位服务只提供 `getStudentHired`（返回 true/false）和 `listJob`（只返回已上架岗位）。岗位一旦招满或下架，历史工时就算不出钱。
- **根因**：接口文档初稿只定义了「录用查询」这一个跨服务接口，遗漏了「岗位详情查询」。
- **修复**：成员 4 于 2026-11-17 23:37 新增 `GET /api/job/getJob?jobId=`（提交 `03023f3`），返回任意状态岗位详情（含 `hourSalary`、`deptId`、`status`）。
- **配套措施**：本服务在**签到时刻**把时薪、部门、岗位名快照进签到记录，结算用快照值，不受后续调薪/下架影响。
- **回归**：TC-01（时薪快照）、TC-11（金额核算）通过。

### BUG-02（功能类 · 高）data.sql 全为注释导致服务启动失败

- **发现人**：成员 5　　发现日期：2026-11-18　　状态：已修复
- **复现**：`data.sql` 只有注释、无任何可执行语句时启动服务。
- **实际**：应用启动失败，`dataSourceScriptDatabaseInitializer` 报错：
  ```
  Failed to execute database script from resource [data.sql]
  Caused by: java.lang.IllegalArgumentException: 'script' must not be null or empty
  ```
  连带 20 个用例全部报错（上下文加载失败）。
- **根因**：Spring 的 `ScriptUtils` 剥离注释后发现脚本为空，直接抛异常，不允许执行空脚本。
- **修复**：`data.sql` 末尾补一条无副作用的 `SELECT 1;` 占位语句，并在文件里注明原因（防止后人"优化"时又删掉）。
- **回归**：全量 20 个用例恢复通过；服务可正常启动。
- **经验**：`schema.sql` / `data.sql` 不要写成纯注释文件。

### BUG-03（构建类 · 中）`mvn spring-boot:run` 在中文路径下启动失败

- **发现人**：成员 5　　发现日期：2026-11-18　　状态：已绕过（建议用打包方式启动）
- **复现**：项目位于 `D:\软件工程大作业\repo`（路径含中文），执行 `mvn spring-boot:run`。
- **实际**：`ClassNotFoundException: com.campus.auth.AuthServiceApplication`，但 `target/classes` 里类文件存在。
- **根因**：spring-boot-maven-plugin 3.3.5 在 Windows 下 fork JVM 时，含中文的 classpath 未按 UTF-8 传递，导致找不到主类（Maven 自身与 surefire 均正常，故 `mvn test` 不受影响）。
- **绕过方案**：
  ```bash

  java -jar target/attendance-service-1.0.0.jar
  ```
  已将三个服务全部用该方式成功启动（8081/8082/8083 同时在线）。
- **根治方案（可选）**：把仓库移到纯英文路径（如 `D:\campus\repo`），或在 VS Code / IDEA 里直接运行 Application 主类（IDE 不走 Maven fork）。

### 已确认：演示账号口令一致（非缺陷）

- `README.md`、`交接说明.md`、`环境搭建指南.md` 与 `src/main/resources/data.sql` 第 2 行注释写的是**同一个六位口令**；
- 校验方式：对 5 个预置账号（admin / deptA / center / student1 / student2）的 BCrypt 哈希逐一 verify，全部匹配该口令；
  并用 `student1` 实际登录，返回 `userId=4, roleId=1`，与预期一致；
- 另取一个常见的六位候选口令对比，对全部账号均不匹配，可排除；
- **结论**：演示脚本可直接使用文档中给出的口令，不需要改动任何文档或注释。
- 备注：库中存的是 BCrypt 加盐哈希，源码无法反推明文，因此采用「哈希比对 + 实际登录」双重验证，
  而不是靠肉眼核对文档——本次一开始误判为"两处文档矛盾"，就是人工比对不可靠导致的。


### BUG-04（并发类 · 高）同岗位并发签到产生两条未签退记录，工时被重复计算

- **发现人**：成员 5　　发现日期：2026-11-18　　状态：已修复
- **环境**：attendance-service 8083，H2（`MODE=MySQL`）
- **复现步骤**：同一学生（userId=4）对同一岗位（jobId=1），用 `CountDownLatch` 同时发起两个 `checkIn` 请求。
- **预期**：只有一条签到成功，另一条返回 400「已签到且未签退」。
- **实际（修复前）**：
  ```
  PROBE_RESULT 线程1=OK
  PROBE_RESULT 线程2=OK
  PROBE_RESULT 总记录数=2 未签退记录数=2
  ```
  两条 `status=0` 记录同时存在，之后两次签退会各自算出工时，**同一段时间被结算两次**。
- **根因**：签到逻辑是「先查有没有未签退记录 → 没有则插入」，查与插之间存在竞态窗口：
  两个请求都查到 0 条，然后都插入成功。数据库层当时只有普通索引 `idx_att_user_time`，
  没有唯一性约束兜底，所以拦不住第二个请求。
- **为什么不能用普通唯一索引修复**：`UNIQUE(user_id, job_id)` 会误伤——同一学生对同一岗位
  历史上有多次签退记录（每天打卡），这些记录必须共存。
- **修复方案（可移植、不依赖进程内锁）**：
  1. 新增列 `active_key VARCHAR(64)`：**未签退期间** = `"userId:jobId"`，签退时置 `NULL`；
  2. 加唯一约束 `CONSTRAINT uk_att_active UNIQUE (active_key)`；
     由于 SQL 标准中多个 `NULL` 不参与唯一性判断（H2 与 MySQL 行为一致），已签退的历史记录互不冲突；
  3. 签到改用 `saveAndFlush` 让冲突立刻抛出，捕获 `DataIntegrityViolationException` 转成
     400「您在该岗位已签到且未签退，请先签退」，而不是让前端看到 500；
  4. 保留原有的前置查重——它不是防线，只是为了大多数场景给出友好提示、少打一次数据库。
- **回归**：
  ```
  PROBE_RESULT 线程1=OK
  PROBE_RESULT 线程2=BusinessException: 您在该岗位已签到且未签退，请先签退
  PROBE_RESULT 总记录数=1 未签退记录数=1
  ```
  已固化为 `AttendanceConcurrencyTests#tc20_concurrentCheckIn`（TC-20），当时全量 23 个用例通过
  （后续补入结算/发放与分页/核实用例，现为 45 个）。
- **经验**：凡"先查后插"的业务唯一性，**必须**有数据库层约束兜底，业务层查重只能算优化。
  另外并发用例不能加 `@Transactional`，否则两个事务互相看不见，测不出问题。

### 联调中暴露的两个问题（均已定性，非代码缺陷）

**问题 1：陈旧数据库导致首轮联调「签到返回 400 但提示已签到」**

- 现象：首次签到返回 400，紧接着的重复签到却提示「已签到且未签退」；75 秒的间隔被算成 6 分钟。
- 排查：查服务 SQL 日志，本轮**没有任何 `insert into t_attendance_record`**，只有 `select` 和一条 `update`，
  说明签到记录在服务启动前就已存在于 `./data/attendancedb.mv.db`。
- 根因：沿用上一轮遗留的 H2 文件库，其中有一条「已签到未签退」的历史记录，签到被"关 3"拦下，
  随后的签退把那条旧记录结算掉，所以工时时长是旧记录的时间差。
- 处置：备份旧库为 `data_bak_before_smoke`、删除 `./data/` 重启（H2 文件库会自动重建），重跑后全部通过。
- **经验**：`attendance-service` 用文件库，联调/演示前必须先 `删除 ./data/ 目录` 再启动，
  否则会带着上一轮的未签退记录进场，表现为"莫名 400"。这一点已写进 README 演示须知。

**问题 2：签退时工作不足 1 分钟被拒（设计如此，非缺陷）**

- 现象：签到后立即签退返回 400。
- 确认：`AttendanceService.checkOut` 中 `minutes < 1` 时抛「签到时长不足 1 分钟，请稍后再签退」，属**有意设计**，
  避免产生 0 分钟垃圾记录。演示脚本因此在签到与签退之间等待 75 秒。

### 观察项（不影响正确性，建议前端处理）

- 1 分钟工时时，接口返回 `workMinutes=1`、`workHours=0.0`、`amount=0.42`。
  小时数按设计保留 1 位小数（`CalcUtils.workHours`），1÷60≈0.0167 四舍五入后为 `0.0`，看起来像"干了活却 0 小时"。
- 金额按**精确分钟**计算，所以结果本身没错（0.42 元）。建议前端展示时以「分钟」或保留 2 位小数显示小时，
  避免与金额不一致造成误解。是否调整展示口径由全组统一决定，本服务暂不改动已通过测试的计算规范。

### 结论

- 三个服务在同一台机器上同时运行、互相调用正常，跨服务鉴权（8081）与录用校验（8082）均真实生效；
- 权限隔离（学生 / 部门管理员 / 中心管理员）与越权拦截（403）全部按预期工作；
- 依赖服务不可用时**写操作拒绝、读操作可用**，降级行为符合设计；
- **结算 → 发放闭环在真机上跑通**：结算金额与实时核算一致（0.42 元），重复结算只刷新不新增，
  发放后再查学生端 `settleStatus=1`；重复发放返回 400，不会重复计数。
- **分页与异常核实**：`myRecord` 的 page/size 回显与合计不变性在真机验证；核实接口的权限
  （学生 403）与状态校验（非异常 400）在真机验证，两条业务分支由 TC-41/TC-42 覆盖
  （真机造 12 小时工时不可行）。
